# Repository Guidelines

`AGENTS.md` is the sole maintained repository instruction file. Edit it directly; do not add duplicate instruction files or synchronization workflows.

## Project direction

- `BP602/KickTalk` is an independently maintained breakaway project. Product decisions, fixes and releases are owned here; this is not a staging fork for contributions to `KickTalkOrg/KickTalk`.
- Default to this repository's development and release workflow. Internal PRs may be used for review; do not plan upstream PRs, rebases or automatic upstream synchronization unless the user explicitly selects that work.
- Preserve original attribution, applicable licenses and Git history. Historical upstream comparisons and retained reference checkouts do not create an integration obligation.
- GitHub's fork-network designation is a separate administrative matter. Do not delete/recreate the repository, discard repository metadata, alter someone else's child fork, or remove preserved local refs/checkouts merely to remove the fork label. Detachment requires a preservation plan and explicit approval of any irreversible effects.


## Project planning and maintenance

- Task board: [KickTalk restart](https://github.com/users/BP602/projects/1/views/1), owned by `BP602`, project `1`. Use it as the source of truth for selected work, priorities, dependencies, and completion evidence.
- Read the project README and relevant cards before substantial work. Reuse an existing card where the scope matches; otherwise create a private draft with the outcome, acceptance criteria, sources, and blockers. Do not start unrelated backlog work without a user request.
- `docs/Restart-board.excalidraw` is the checkout map, not a second live task tracker. Keep its folder roles accurate when checkouts change; maintain task status in GitHub Projects.

### Maintain cards while working

- `Backlog`: historical reports or unselected work. `Ready`: scoped work with prerequisites satisfied. `In progress`: work actually underway. `In review`: awaiting review or acceptance evidence. `Done`: acceptance criteria met with recorded evidence.
- When starting a selected task, move its card to `In progress`. Keep one primary restart card active; delegated subtasks remain within that card's scope.
- Update the card at meaningful checkpoints, scope changes, and blockers, not for every tool call. Record decisions and the specific information needed to unblock work.
- There is no `Blocked` status in the current workflow. Keep unstarted blocked work in `Backlog` with a `Blocked by` section; use `In review` only when implementation is complete and review or validation is pending. Do not leave blocked work marked `Ready` or actively `In progress`.
- Move a card to `Done` only after exercising the changed behavior and satisfying its acceptance criteria. Record the result, relevant commit/PR or file references, and any untested behavior or unresolved failures. A successful build alone does not prove live chat or sending works.
- Before handoff, sync the relevant card's status and evidence, or explicitly report why it could not be synced. Do not mark preservation, consolidation, or fixes complete merely because a plan was written.
- Revalidate historical issues and PRs against current code, discussion, and GitHub state before changing their disposition. Do not bulk-close old cards, alter the workflow, or treat old performance/security claims as current findings without evidence.

### Recovery boundaries

- Preserve all checkouts, stash objects, and uncommitted/untracked work before integration. An ordinary clone does not preserve dirty files or all stashes.
- A board card is not permission to pop/drop stashes, hard-reset, prune refs, force-push, delete branches, or mass-apply an old cherry-pick script. Require explicit authorization for destructive recovery actions.
- Keep unrelated old work archived for selective review. Do not import the entire testing branch or begin a framework migration as part of establishing the restart baseline.

### Daily development

- `~/Code/KickTalk` on local `main` is the canonical daily checkout. `~/Code/KickTalk-restart` is retained for integration and recovery, not daily work; removing it requires explicit approval.
- Start selected work on a small, short-lived `fix/*`, `feat/*`, or appropriate Conventional Commit topic branch from local `main`. Keep the existing lockfile-respecting install and acceptance-evidence workflow.
- The checkpoint, archive locations, and exact recovery snapshot are documented in [README.md](README.md#restart-baseline). Recover historical edits in a separate worktree; do not reapply the pre-promotion snapshot onto daily `main`.
- Promotion is a local development checkpoint. It does not authorize a push, release, branch deletion, or stash cleanup, and it does not resolve the recorded failed-send or dependency risks.

## Electron‑Vite Patterns

- App stack: electron‑vite + React. Prefer electron‑vite conventions over raw Electron.
- Preload loading: from main, point to the built preload (e.g., `join(__dirname, '../preload/index.js')`); in ESM, use `fileURLToPath(new URL('../preload/index.js', import.meta.url))`.
- Security: keep `contextIsolation: true`; avoid direct Node APIs in renderer.
- Assets: resolve via Vite URLs (e.g., `new URL('./icon.png', import.meta.url)`).
- Docs: when unsure, use Context7 to consult electron‑vite/Electron/Vite docs and confirm patterns.

## Project Structure

- Source root: `src/`
- Main (Electron, Node context): `src/main/`
- Preload bridges: `src/preload/`
- Renderer (React): `src/renderer/src/**` (components, hooks, assets, styles)
- Telemetry: `src/telemetry/**`, `src/renderer/src/telemetry/**`
- Build output: bundled `out/`; installers in `dist/`
- Config: `electron.vite.config.mjs` (main, preload, renderer builds)
- Docs/examples: `docs/`; load/perf artifacts: `tests/`

## Preload Bridges

- API surface: expose minimal, purpose‑built functions via `contextBridge.exposeInMainWorld`.
- Isolation: keep `contextIsolation: true` and avoid exposing raw Node.
- Contract: document each exposed method and validate inputs on the main side.

## IPC Model

- Request/response: main registers `ipcMain.handle('channel', fn)`; renderer calls `ipcRenderer.invoke('channel', payload)`.
- Events: use `ipcRenderer.send`/`ipcMain.on` for fire‑and‑forget; prefer namespaced channels like `app:settings:get`.
- Safety: validate/sanitize payloads in main; avoid wildcards and dynamic eval.
- Example: renderer `await window.electron.ping()` ↔ main `ipcMain.handle('ping', () => 'pong')`.

## Env & Secrets

- Access: use `import.meta.env` with electron‑vite’s scoped prefixes.
- Default prefixes (active):
  - Context‑scoped: `MAIN_VITE_*` (main), `PRELOAD_VITE_*` (preload), `RENDERER_VITE_*` (renderer)
  - Shared non‑secrets: `VITE_*`
  - Unprefixed keys are ignored by Vite.
- KickTalk naming:
  - Use `MAIN_VITE_KT_*`, `PRELOAD_VITE_KT_*`, `RENDERER_VITE_KT_*` for app‑specific vars per context.
  - Avoid bare `KT_*` in renderer; it is not exposed via `import.meta.env` with the default config.
  - If you need bare `KT_*` available, add an `envPrefix` override in `electron.vite.config.mjs` (not enabled now).
- Secrets: keep in `process.env`/`MAIN_VITE_*` (main only); never expose secrets to renderer.
- Setup: create `.env` from `.env.example`. Packaging excludes docs/tests—avoid bloat.

## Telemetry

- Instrumentation: OpenTelemetry under `src/telemetry/**` and `src/renderer/src/telemetry/**`.
- Export: send traces/metrics directly to Grafana Cloud via OTLP HTTP (no collector).
- Config: set OTLP endpoint/keys via `.env` using main‑safe prefixes (see “Env & Secrets”). Never expose secrets to renderer.

## Testing

- Runner: Vitest. Run `npm run test:realtime` for the controller, IPC adapter, room-manager/7TV routing and collector/analyzer suites in `tests/kickRealtime.test.js`, `tests/kickRealtimeClient.test.js`, `tests/connectionManager.test.js` and `tests/eventAnalyzer.test.js`.
- Transport fixtures use real loopback HTTP/WebSocket traffic and synthetic credentials; tests must not access Kick or a saved account.
- For React component tests, use React Testing Library with Vitest. Naming: `Component.test.jsx`; colocate or use `__tests__/`.
- Keep tests deterministic and isolated; stub Electron bridges only at their public seam.
- Live sends, deletions and moderation require explicit approval for the exact account, room and action. Verify the target immediately before the mutation; never infer it from an asynchronously changing active composer or automatically retry a live test message.

# When you need to call tools from the shell, **use this rubric**:

- Find Files: `fd`
- Find Text: `rg` (ripgrep)
- Find Code Structure (TS/TSX): `ast-grep`
  - **Default to TypeScript:**  
    - `.ts` → `ast-grep --lang ts -p '<pattern>'`  
    - `.tsx` (React) → `ast-grep --lang tsx -p '<pattern>'`
    - `.js` → `ast-grep --lang js -p '<pattern>'`
    - `.jsx` (React) → `ast-grep --lang jsx -p '<pattern>'`
    - JSON → `ast-grep --lang json -p '<pattern>'`
  - For other languages, set `--lang` appropriately (e.g., `--lang rust`).
- Select among matches: pipe to `fzf`
- JSON: `jq`
- YAML/XML: `yq`

If ast-grep is available avoid tools `rg` or `grep` unless a plain‑text search is explicitly requested.
